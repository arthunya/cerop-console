CEROP is a graduate machine-learning project I built with three classmates. It answers two questions a company buying from abroad keeps asking: will this supplier still be in business, and will this shipment arrive on time? Over the next few minutes I'll show how we built two models for those questions, how we checked them, and where they fall short.
The problem

Cross-border buyers carry two risks

A supplier failing

Owned by credit and procurement. They read balance sheets and decide whether to extend terms or renew a contract.

Goods arriving late

Owned by logistics. They watch orders and decide where to add buffer stock or chase a carrier.

Commercial risk scores exist, but they're paid for, refreshed every so often, and rarely say why a score is what it is.

The two risks sit with different teams. A credit analyst worries about whether a supplier survives the year. A logistics planner worries about this week's shipment. Commercial tools already score suppliers, which shows the need is real, but they are proprietary and mostly opaque. We wanted to see how far public data and transparent methods could get.
What CEROP does

Two independent models, on purpose

Supplier risk

XGBoost on {{ facts.financial.features | int }} financial ratios. Output: the chance a firm goes bankrupt, plus the factors behind it.

Shipment delay

Random Forest on {{ facts.operations.model_features | int }} order features. Output: the chance an order arrives late, plus the factors behind it.

They're deliberately not merged. A solvent supplier can still ship late, and a failing one can ship on time right up to the end. One blended number would hide what each team needs to see.
CEROP keeps the two answers apart. Each model is trained on its own data, judged with its own metric, and shown to its own audience. We considered a single combined score and rejected it, because averaging a financial signal with a delivery signal hides exactly the detail each team acts on.

One rule throughout: split first, then fit. Scalers, encoders and clipping bounds learn from training data only.

Both layers follow the same eight steps. The one rule that held it together was to split the data before fitting anything. Every scaler, encoder and clipping bound learned from the training split only. If any of them had seen the test data, our test scores would have been quietly optimistic.
Catching leakage

A model that knows the answer looks great and fails

  • Actual shipping days and delivery status were the strongest predictors of lateness, and both are only known after delivery. Removed in Week 4.
  • Order Status: kept in Week 4, then judged a possible leak in Week 6 and dropped, taking the model from {{ facts.operations.processed_features | int }} to {{ facts.operations.model_features | int }} inputs.
  • An unreliable tail: orders from October 2017 on behaved erratically, so {{ derived.ops_rows_removed | int }} rows were removed before the split.
  • Checks that must pass before any model runs: no missing values, every value finite, train and test with the same columns.

Notebook 03 (asserts in cells 10 and 32); row counts from Final Report Table 5.

Leakage is the most common way a student project fools itself. The column most correlated with lateness was the number of days the shipment actually took, which you only know afterwards. We removed it, removed the delivery status, and later dropped the Order Status columns too. We also cut an unreliable stretch of data at the end of 2017.
Choosing the financial model

Why 97% accuracy is the wrong metric

Test set, threshold 0.50. Final Report Table 7.

A model that calls every firm safe would be {{ derived.always_no_accuracy | pct1 }} accurate on our test set and catch nothing.

So we compared recall, precision and F1. Logistic Regression catches the most failures (recall {{ finrep.logreg.recall | f3 }}) but most of its alarms are wrong (precision {{ finrep.logreg.precision | f3 }}).

XGBoost has the best balance: F1 {{ finrep.xgb.f1 | f3 }}, ROC-AUC {{ finrep.xgb.roc_auc | f3 }}.

With three percent positives, accuracy is meaningless: always saying no scores nearly ninety-seven percent. So we compared the models on recall, precision and F1. Logistic Regression catches the most failures but floods the analyst with false alarms. XGBoost gave the best balance, with Random Forest close behind as a fallback.

A model gives a probability. Calling an order late at fifty percent is just a convention. We chose the line on a validation set, picking the best F1, which landed at 0.40. On the test set that caught about thirty-seven hundred more late shipments and raised about forty-two hundred more false alarms. The console lets you move that line yourself.
Explaining each case

Real SHAP, checked to add up

For every case shown, the starting point plus all feature contributions equals the score within 1e-6. Scheduled days and shipping mode carry the same information in this data, so read them together.

results/web/financial_shap_cases.json, operations_shap_cases.json (notebook 07). Numbers are percentage points.

Every score comes with a reason. These are SHAP values computed from the exported model files, in the same units as the score. Before a case is shown, we check that the starting point plus every contribution adds up to the score. The top drivers rarely explain everything, so the remainder always gets its own line.

Limits and lessons

What this can't tell you

  • Results moved between runs: F1 {{ fin.reproduced.f1 | f3 }} locally vs {{ fin.official.f1 | f3 }} reported, same code and seed. Library versions.
  • Only {{ facts.financial.test_bankrupt | int }} bankrupt test firms, so wide uncertainty.
  • Taiwan, 1999–2009: not validated elsewhere.
  • Collinear shipping features: scheduled days and shipping mode are one signal.
  • Prototype scope: no monitoring, retraining or live feed.

What I'd do next

  • Pin library versions from day one.
  • Bootstrap intervals on every headline metric.
  • Export one raw-to-probability pipeline per layer.
  • Pick thresholds from real costs, not F1.
  • Test on newer, non-Taiwanese data.
Honest limits. Re-running the same notebook on a different machine changed the financial F1 slightly, which taught me to pin library versions early. There are only forty-four bankruptcies to test on, the data is Taiwanese and old, and two shipping features are really one. Next, I'd add error bars and choose thresholds from actual costs.
