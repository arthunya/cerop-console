That's worth saying plainly instead of burying. With {{ facts.financial.test_bankrupt | int }} bankruptcies in the test set, the financial difference is a couple of firms either way. The Week 6 notebook checked this with a paired bootstrap ({{ fin.tuning.bootstrap.n_resamples | int }} resamples of the test set): the 95% interval for the change in PR-AUC runs from {{ fin.tuning.bootstrap.ci_low | f3 }} to {{ fin.tuning.bootstrap.ci_high | f3 }}, which includes zero, so the drop can't be told apart from noise. On the operations side the tuned forest did rank orders a little better (ROC-AUC {{ opsDef.roc_auc | f3 }} against {{ opsBase.roc_auc | f3 }}), it just didn't turn that into a better F1 at 0.50. The financial layer therefore kept its Week 5 XGBoost.

The financial search fit on a {{ report.t09.r1.c1 | int }}-firm tuning split and held out {{ report.t09.r2.c1 | int }} firms for validation (Final Report Table 9), so its F1 values aren't directly comparable with the full-training-set result of {{ fin.official.f1 | f3 }}.

The threshold is a business decision

A classifier outputs a probability. Calling an order "likely late" at 0.50 is a convention, not a law. Lower the line and you catch more late orders but raise more false alarms. Raise it and the reverse happens. Which side is cheaper depends on the business.

For operations, the team picked the threshold with the best F1 on a validation set carved out of the training data, so the test set stayed untouched until the very end.

A note on the two runs

The Week 6 notebook was run twice. The team's Colab run, which the submitted reports quote, selected a threshold of {{ colabCal.threshold | t2 }} and reached recall {{ colabCal.recall | f3 }} and F1 {{ colabCal.f1 | f3 }}. The notebook was re-run locally in August to export the final model, and that run selected {{ ops.calibrated_threshold | t2 }}. The model file behind the console comes from the second run, so this site uses its numbers everywhere. Both sets of result files are in the repo.

What changed because of it

The financial layer stays at 0.50, because tuning and threshold moves didn't give a dependable gain on {{ facts.financial.test_bankrupt | int }} positives. The operations layer ships at {{ ops.calibrated_threshold | t2 }}, and the console lets you move that line yourself.
